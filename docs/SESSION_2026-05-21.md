## 1. Ausgangslage

### Hardware
- **M5Stack Dial** (StampS3, ESP32-S3) — BLE Central
- **123\TUNE+ Zündverteiler** mit nRF52810, Albertronic "UART AT Command" v1.4c — BLE Peripheral
- MAC: `ef:a8:b2:de:e0:9e`
- Verbindung: USB COM4 (ESP32-S3 nativ)

### Software-Stack
- PlatformIO + Arduino-ESP32
- **NimBLE-Arduino 2.5.0** (aktuell `^2.0.0` in `platformio.ini`)
- M5GFX 0.2.21 (Display)

### Ziel
M5Dial soll Zündungs-Telemetrie via BLE NUS empfangen und auf GC9A01 anzeigen:
- Service: `6e400001-b5a3-f393-e0a9-e50e24dcca9e`
- TX Notify: `6e400003-b5a3-f393-e0a9-e50e24dcca9e`
- Frame-Format: 5 Bytes ASCII (Type, hi-hex, lo-hex, Checksum, Terminator 0x20)
- Frame-Typen: `0x30`=RPM, `0x31`=ADV, `0x32`=MAP, `0x33`=TEMP, `0x35`=CURR, `0x41`=VOLT

## 2. Beobachtetes Problem

```
Verbinden          → OK
Subscribe(NUS TX)  → "OK" zurück, CCCD readback = 0x0001
                   → ABER null Notifications auf Handle 15
Subscribe(Battery) → OK + sofortige Notifications auf Handle 29 (single byte)
~10-20s später     → Disc reason=520 (Supervision Timeout)
```

### Wichtige Vergleichspunkte
- **iPhone nRF Connect**: empfängt **alle** NUS-Frames, Motor läuft, Werte ändern sich ✅
- **Android nRF Connect**: laut User "gestern" auch funktionierend mit Werten ✅
- **Windows nRF Connect**: Services sichtbar, Notification-Empfang unklar

→ Das Gerät **sendet** also auf NUS TX, aber nur an bestimmte Centrals.

## 5. Ausgeschlossene Ursachen

| Hypothese | Ergebnis | Beleg |
|---|---|---|
| Falsche Subscribe-Signatur | ❌ ausgeschlossen | V2 zeigte CCCD=0x0001 |
| `response=false` (Write Without Response) | ❌ ausgeschlossen | V2-V4 mit `response=true` gleiches Verhalten |
| Connection Params zu aggressiv | ❌ ausgeschlossen | V3+ akzeptiert Slave-Wunsch, gleiches Verhalten |
| MTU zu klein | ❌ unwahrscheinlich | 5-Byte Frames passen in MTU 23, Battery kommt durch |
| Falsche Char/Handle | ❌ ausgeschlossen | Full GATT-Dump zeigt keine andere notify-Char |
| Slave sendet gar nicht | ❌ ausgeschlossen | iPhone bekommt Frames, ParaReq beweist Slave aktiv |
| Falscher Service-UUID | ❌ ausgeschlossen | NUS-UUIDs stimmen mit Spec überein |

## 6. Offene Hypothesen (priorisiert)

### H1 — Encryption/Bonding-Pflicht auf NUS TX CCCD (gerade getestet)
- iPhone/Android pairen oft transparent
- NimBLE 2.x default ist No-Auth
- **Test**: V5 aktiv, Result ausstehend

### H2 — Slave erwartet bestimmten "Init-Trigger" / Command
- z.B. spezielles Write auf RX vor Subscribe
- Bisher getestet: `0x01`, `"START\r\n"` → sofortiger Disconnect
- Ungestestet: andere Magic-Bytes

### H3 — Slave hat Bug bei zwei gleichzeitigen Subscriptions
- Wir subscriben NUS TX **und** Battery
- Vielleicht "klaut" Battery den Notification-Slot
- **Test**: nur NUS, nicht Battery

### H4 — Connection Update wird nicht akzeptiert wie erwartet
- Slave schickt `ParaReq 16-32 L0 T400` 4s nach Connect
- Wir akzeptieren mit `return true`
- Vielleicht zu spät — könnten beim Connect bereits diese Params setzen
- **Test**: `setConnectionParams(16, 32, 0, 400)` **vor** `connect()` wieder rein

### H5 — Subscribe-Reihenfolge wichtig
- Aktuell: NUS zuerst, dann Battery
- Vielleicht andersrum nötig

### H6 — Slave hat Whitelist/Bonded-Device-Filter
- Sendet NUS-Daten nur an bekannte (bonded) Centrals
- Dann wäre H1 die Lösung

## 12. Update 2026-05-22: internes Logging + WebGUI

- Firmware schreibt jetzt lokal CSV nach SPIFFS:

```text
/drive.csv
/drive_old.csv
```

- CSV-Spalten ab Firmware-Update 2026-05-22:

```csv
ms;zeit;epoch;rpm;zuendung_grad;map_kpa;temp_c;spannung_v;spule_a;rx
```

- Geloggt wird nur bei RPM > 650 U/min.
- Sobald Home-WLAN verbunden ist, startet die Firmware NTP mit deutscher
  Zeitzone. Danach steht in `zeit` lokale Uhrzeit, z.B.
  `2026-05-22 14:39:12`, und in `epoch` die Unix-Zeit.
- Die M5Dial-RTC BM8563 wird auf I2C `SDA=G11` / `SCL=G12` genutzt:
  - beim Boot wird die Systemzeit aus RTC geladen, wenn plausibel
  - nach erfolgreicher NTP-Zeit wird die RTC gesetzt
  - mit Batterie kann die Zeit damit auch ohne WLAN ueber Neustarts weiterlaufen
- Ohne plausible RTC und ohne WLAN/NTP faellt `zeit` weiter auf `BOOT+millis`
  zurueck und `epoch` ist `0`.
- CSV ist absichtlich semikolon-getrennt und nutzt Dezimalkomma fuer Excel/DE.
- Beim ersten Start mit neuem CSV-Format wird ein altes Komma-CSV automatisch
  nach `/drive_old.csv` rotiert.
- Falls NTP im lokalen Netz nicht antwortet, kann die WebGUI die Zeit direkt
  aus Browser/Laptop setzen (`Sync from browser`) und ebenfalls in die RTC
  schreiben.
- WebGUI laeuft auf Port 80:
  - aktuelles CSV herunterladen
  - rotiertes altes CSV herunterladen
  - aktuelles Log loeschen
  - WLAN-Daten speichern
  - WPS starten

Wenn keine WLAN-Daten gespeichert sind:

```text
SSID:     M5Dial-123-Setup
Passwort: offen
URL:      http://192.168.4.1/
```

Zusatz: Die seriellen Kommandos `wifi_status` und `time_status` zeigen IP,
gespeicherte WLAN-Konfiguration und aktuellen Zeitstatus. Mit
`time_set <epoch>` kann die Uhr auch per USB gesetzt werden.

WPS mit FRITZ!Box:

1. Mit `M5Dial-123-Setup` verbinden.
2. `http://192.168.4.1/` oeffnen.
3. `Start WPS` anklicken.
4. An der FRITZ!Box `Connect/WPS` druecken.
5. M5Dial speichert SSID/Passwort in NVS.
